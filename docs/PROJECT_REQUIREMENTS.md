교육과정 온톨로지·지식그래프 기반 설명 가능한 로컬 조교 챗봇
프로젝트 분석·설계·개선 및 구현 지시문

당신은 이 프로젝트의 온톨로지 설계자, 지식그래프·규칙 검증 엔지니어, 백엔드·프론트엔드 기술 리드, 평가 담당자입니다. 아래 요구사항을 기준으로 제공된 자료와 기존 구현을 분석하고, 문제의 원인을 확인한 뒤 개선안을 설계하고 구현·검증하세요. 단순히 좋은 LLM으로 바꾸거나 프롬프트를 길게 만드는 해결책보다 지식 구조와 결정적 검증 로직의 완성도를 우선하세요.

이 문서의 예시 관계와 처리 흐름은 설계 방향을 설명하기 위한 것입니다. 실제 PDF에 없는 교육과정 규칙, 학점 수치, 인정 관계를 만들어 넣으라는 뜻이 아닙니다.


1. 프로젝트의 목적

현재 등록된 공식 규정 문서 집합을 기준으로 온톨로지와 지식그래프를 구축하고, 이를 사용하는 Graph RAG 기반의 조교형 챗봇을 개발합니다. 현행 공식 집합에는 「2026년도 교육과정」 PDF 한 건만 등록되어 있습니다. 실행 환경은 RTX 4070 Ti가 장착된 현재 PC이며, 자연어 처리는 로컬 LLM으로 수행합니다.

이 시스템은 PDF에서 관련 문단을 찾아 요약하는 데 그치면 안 됩니다. 학생의 이수 내역과 교육과정의 관계·규칙을 연결하여, 학생이 PDF를 직접 읽거나 일반적인 문단 검색형 RAG만 사용해서는 풀기 어려운 복잡한 질문에 답해야 합니다.

핵심 목표는 다음과 같습니다.
- PDF에서 바로 확인 가능한 사실 질문에 정확히 답합니다.
- 여러 과목·이수 구분·적용 조건·예외·학생 이수 정보를 함께 고려해야 하는 관계형 질문에 답합니다.
- 적용되는 졸업 조건의 충족 여부, 부족한 요건, 특정 과목을 추가 이수했을 때의 변화를 계산합니다.
- 결론이 어떤 실제 관계와 규칙 검증을 통해 나왔는지 한국어로 설명합니다.
- 근거 없는 사실을 생성하지 않으며, 미확인 정보와 확인된 사실을 명확히 구분합니다.

성능의 중심은 LLM이 아니라 온톨로지, 지식그래프, 조회 로직, 규칙 검증 로직이어야 합니다. 화면이나 그래프를 화려하게 꾸미는 것보다 답변의 정확성과 실제 작동하는 결과물을 우선하세요.

- 문서에 없는 규칙을 일반적인 대학 관행이나 LLM의 사전 지식으로 보충하지 마세요.

3. LLM과 지식그래프·검증 로직의 역할 분담

로컬 LLM의 런타임 역할은 다음 두 가지로 제한합니다.
- 자연어 질문을 해석하여 의도, 과목, 조건, 대화 맥락 등을 구조화된 입력으로 변환합니다.
- 지식그래프와 검증 로직이 산출한 결과를 자연스러운 한국어 답변으로 표현합니다.

다음 작업은 LLM의 자유로운 추론에 맡기지 마세요.
- 교육과정 규칙의 생성 또는 변경
- 학생에게 적용되는 조건의 최종 확정
- 학점 합산, 중복 제거, 대체·면제·인정 처리
- 졸업 요건 충족 여부 및 최종 판정
- 근거가 없는 과목 관계나 학생 이수 사실의 보완
- 실행하지 않은 조회·탐색·검증 과정의 생성

이 작업은 검증 가능한 그래프 조회와 결정적 규칙 검증 코드로 수행합니다. 모든 계산을 억지로 그래프 안에서 처리할 필요는 없지만, 판단에 필요한 사실과 관계는 구조화되어 있어야 하며 계산·판정은 재현 가능해야 합니다.

LLM이 해석에 참여하므로 모델의 영향이 완전히 없어지는 것은 아닙니다. 대신 동일한 의미의 검증된 구조화 입력과 동일한 데이터·규칙 버전이 주어지면, 모델이 달라도 사실·계산·최종 판정은 같아야 합니다.

LLM이 만든 자유 형식의 쿼리나 규칙을 검증 없이 실행하지 마세요. 검증된 의도와 매개변수를 허용된 조회 계획에 연결하고, 스키마·값·권한 검증을 적용하세요.

최종 답변은 구조화된 판정 결과와 일치해야 합니다. LLM이 수치, 판정, 조건, 출처를 바꾸거나 새로운 사실을 추가하면 검증에서 차단하고, 검증된 결과를 사용하는 정형 답변으로 대체하세요.


4. 졸업 가능 여부의 판정 범위

졸업 판정은 현재 시스템에 등록된 **AuthoritativeDocumentSet**에서 해당 학생에게 적용되는 모든 VERIFIED 요건을 확정한 **CurriculumRuleSet** 버전을 기준으로 합니다. 현재 v1에는 「2026년도 교육과정」 PDF만 포함되므로 기존 2026 컴퓨터공학과 Core 판정 의미는 유지합니다. 모든 적용 요건이 충족되면 해당 규정 집합 및 RuleSet 버전 기준으로 졸업 가능이라고 판정합니다.

새 공식 문서는 출처·공식성·적용 범위·시행/개정 관계를 검증한 뒤 새 문서집합과 RuleSet 버전에만 반영합니다. 기존 Rule과 Decision은 당시 버전을 보존하여 같은 학생 상태로 재현할 수 있어야 합니다. 보완·명확화·대체·충돌은 근거 있는 관계로 구분하고, 발행일이 늦다는 이유만으로 우선 적용하지 않습니다. 판정에 영향을 주는 미해결 문서 충돌은 `NEEDS_INFORMATION`으로 남깁니다. 평가 전용 자료는 공식 문서집합에 포함하지 않으며, 학생 업로드 자료는 규칙 원천이 아닙니다.

해당 학생에게 적용되는 PDF 내 졸업 조건이 모두 충족되었다고 확인되면, 반드시 “해당 PDF 기준 졸업 가능”이라고 판정하세요. PDF에 없는 요건을 임의로 추가하거나, 막연히 학교에 문의해야 한다는 이유로 판정을 회피하지 마세요.

상태는 다음을 구분해야 합니다.
- 충족: 필요한 사실이 확인되었고 적용 조건을 만족합니다.
- 미충족: 필요한 사실이 확인되었고 적용 조건을 만족하지 못합니다.
- 확인 필요: 판단에 필요한 학생 정보, 자료의 완전성, 적용 조건 등을 확인할 수 없습니다.
- 적용 대상 아님: 문서상 해당 학생에게 적용되지 않는 조건입니다.

전체 결론은 다음과 같이 구성합니다.
- 모든 적용 조건이 확인·충족됨: “해당 PDF 기준 졸업 가능”
- 하나 이상의 적용 조건이 확인된 미충족 상태임: “해당 PDF 기준 졸업 요건 미충족”과 구체적인 부족 요건 제시
- 확인된 미충족 조건은 없지만 필수 정보가 부족함: 확인된 충족 항목을 먼저 제시하고 “졸업 가능 여부 확인 필요” 및 필요한 정보 제시
- 미충족 조건과 확인 필요 조건이 함께 있음: 두 상태를 구분하여 함께 제시

일부 규칙만 적재되었는데 적재된 규칙을 모두 통과했다는 이유로 졸업 가능이라고 판정하면 안 됩니다. 원문 대비 적용 요건의 구조화 범위와 학생 자료의 범위가 충분한지 확인해야 합니다. 반대로 이미 필요한 정보가 모두 있는데도 불필요한 확인 질문으로 판정을 지연하지 마세요.

문서의 발행 연도, 학생의 입학 연도, 적용 교육과정 연도는 자동으로 같은 것으로 취급하지 마세요. 적용 관계는 PDF의 명시 조건과 확인된 학생 정보에 따라 결정하세요.


5. 온톨로지와 지식그래프 설계 원칙

문단이나 PDF 페이지를 노드로 만들고 유사도 검색만 수행하는 구조로 끝내지 마세요. 교육과정의 의미, 관계, 적용 조건을 실제 질의와 검증이 가능한 형태로 표현해야 합니다.

실제 문서에 필요한 범위에서 다음 개념과 관계를 검토하세요.
- 학생, 학과·전공, 입학 연도, 적용 교육과정과 버전
- 과목, 과목 코드, 학점, 이수 구분, 영역·과목군
- 학생의 이수 기록, 인정 상태, 재이수·중복 관련 정보
- 졸업 요건, 세부 조건, 적용 대상, 예외, 면제, 대체·동일 과목 관계
- 각 사실과 규칙의 원문 출처

명칭만 보고 인정 관계를 추정하지 마세요. 과목의 이수 구분이 교육과정이나 학생의 적용 조건에 따라 달라질 수 있다면, 과목에 전역 속성 하나를 붙이는 방식으로 단순화하지 마세요.

규칙은 문서에 실제로 명시된 경우에 한해 다음처럼 계산 가능한 구조로 표현하세요.
- 필수 과목 전체 이수
- 특정 집합에서 정해진 개수 이상 선택
- 영역별·전체 학점 합산
- AND·OR 조건과 중첩 조건
- 중복 인정 제한과 인정 상한
- 대체·면제·예외와 적용 범위

표, 각주, 예외를 분리 추출하면서 의미가 사라지지 않도록 하세요. 규칙에 필요한 관계가 누락되었는지, 방향·대상·적용 범위가 잘못 연결되었는지 검증하세요.

교육과정 규칙은 버전 관리하고, 학생 개인 데이터는 세션 또는 사용자 단위로 분리하세요. 학생이 내용을 정정하면 이전 상태로 계산한 결과를 그대로 재사용하지 말고 영향을 받는 결과를 다시 계산하세요.

벡터 검색은 용어 후보나 원문 위치를 찾는 보조 수단으로 사용할 수 있습니다. 그러나 검색된 문단을 LLM에게 읽혀 최종 졸업 판정을 맡기는 방식은 목표 구조가 아닙니다.


6. 자연어 질문, 줄임말, 오타, 암시적 정보 처리

사용자가 정확한 공식 명칭과 모든 조건을 한 번에 입력해야만 작동하는 시스템을 만들지 마세요.

다음 입력을 처리해야 합니다.
- “컴공”과 같은 일반적인 줄임말
- “고급자료구조”를 “고자구”라고 표현하는 과목 약칭
- 맞춤법, 띄어쓰기, 오타
- “이거”, “그 과목”, “그럼 하나 더 들으면?”처럼 이전 대화에 의존하는 표현
- 학생이 앞서 말했거나 업로드한 자료에 있어서 현재 질문에서는 생략한 정보
- 여러 요건을 동시에 묻는 질문과 가정·비교 질문

과목 코드·공식 명칭·일반적으로 정의한 별칭·문자열 유사도·대화 맥락을 조합하여 후보를 찾고, 실제 그래프에 존재하는 개체로 연결하세요. 별칭을 평가 문항에서만 추출하여 해당 표현에만 맞추지 마세요.

의미 해석과 사실 생성을 구분하세요. 대화나 자료로 확인되는 정보는 재활용하되, 입학 연도·이수 여부·인정 여부처럼 결론에 영향을 주는 사실을 임의로 추정하지 마세요.

여러 후보가 가능하면 실제 후보를 보여주거나 조건별 답변을 제시하세요. 모호함이 결론에 영향을 주지 않는 부분은 먼저 답하고, 꼭 필요한 정보만 추가로 질문하세요. 질문이 구어체이거나 일부 정보를 암시한다는 이유로 답변 전체를 거부하지 마세요.

실제 이수와 가정 이수를 분리하세요. “이 과목을 들으면?”에 대한 시뮬레이션 결과를 학생의 실제 이수 내역에 자동 반영하면 안 됩니다.


7. 필수 질문 처리 능력과 답변 방식

최소한 다음 유형을 구분하여 처리하세요.

A. 직접 사실 확인
예: “이 과목은 몇 학점이야?”, “이 조건은 어디에 나와?”
답변: 확인된 사실과 적용 범위를 간단히 답하고 원문 근거를 제공합니다.

B. 학생 이수 현황 기반 요건 점검
예: “이수 내역을 보고 뭐가 부족한지 알려줘.”
답변: 적용 요건별 요구량·인정량·부족량 또는 미충족 조건을 계산하고, 충족·미충족·확인 필요를 구분합니다.

C. 복수 관계·규칙이 필요한 질문
예: “이 과목이 어느 조건에 인정되고, 다른 조건에도 같이 인정돼?”
답변: 인정 관계, 중복 인정 제한, 적용 예외를 조회·검증하여 결론을 냅니다.

D. 가정·비교 질문
예: “이 과목을 추가로 들으면 뭐가 달라져?”, “둘 중 어느 과목이 남은 조건을 더 채워줘?”
답변: 동일한 현재 상태를 기준으로 가정별 요건 충족 변화와 남는 조건을 비교합니다.

E. 다음 행동 제안
예: “앞으로 뭐 더 들어야 해?”
답변: 미충족 요건과 연결되는 과목 또는 선택 조건을 근거와 함께 제시합니다. PDF만으로 다음 학기 개설 여부나 실제 수강 가능성을 확인할 수 없다면, 요건상 후보와 실제 수강 가능 여부를 구분합니다.

F. 졸업 가능 여부
예: “지금 이 상태로 졸업할 수 있어?”
답변: 4절의 판정 기준을 적용하고, 학생이 바로 이해할 수 있도록 결론과 이유를 먼저 보여줍니다.

답변의 기본 순서는 “질문에 대한 결론 → 핵심 이유와 수치 → 남은 조건 또는 다음 행동 → 필요한 경우 추가 확인 사항”입니다. 짧은 사실 질문에 모든 내부 정보를 길게 나열하지 마세요. 세부 관계와 원문 근거는 펼쳐보기로 제공합니다.

답변 예시와 테스트 정답의 학점·과목·조건은 실제 PDF에서 확인하여 작성하세요. 확인하지 않은 수치를 실제 규정처럼 제시하지 마세요.


8. 실제 실행 기반의 설명 가능성과 실행 기록

설명의 핵심은 PDF 몇 페이지를 찾았는지가 아니라, 어떤 관계와 규칙을 사용하여 결론이 나왔는지입니다. 원문 위치는 그 관계와 규칙을 확인하는 근거로 함께 제공합니다.

권장 처리 흐름은 다음과 같습니다. 실제 구현에 맞게 구체화하되 역할 경계를 지키세요.

자연어 질문 및 업로드 자료
→ 대화 맥락과 학생 상태 확인
→ 질문 의도·조건의 구조화
→ 과목·교육과정 등 개체 연결 및 입력 검증
→ 허용된 그래프 조회 계획 선택·실행
→ 적용 규칙 선택과 학점·조건 검증
→ 구조화된 판정 결과 및 실제 실행 기록 생성
→ 로컬 LLM의 한국어 답변 표현
→ 판정·수치·근거 일치 검증
→ 답변과 펼쳐보기 근거 표시

각 답변에 연결되는 실행 기록에는 실제 수행한 범위에서 다음 정보를 남기세요.
- 사용한 질문 해석, 확인된 입력과 명시적인 가정
- 조회 작업, 매개변수, 사용한 데이터·규칙 버전
- 조회 결과 중 판단에 사용된 노드 ID와 간선 ID 또는 이에 준하는 식별자
- 적용 규칙 ID, 입력값, 계산·비교 내용, 검증 결과
- 결론에 사용된 사실과 원문 출처
- 누락 정보, 제외한 후보와 그 사유, 실패 상태
- 실제 기록된 실행 단계의 순서

PDF 근거는 가능하면 파일 식별자, PDF 페이지, 인쇄된 쪽수, 절·표·각주 또는 문장 위치로 연결하세요. 해당 항목이 없는 경우 만들어내지 마세요.

관계 그래프와 계산·규칙 검증은 구분해서 설명하세요. 예를 들어 학생·이수내역·과목·인정구분·요건의 연결은 그래프로, 학점 합산과 기준 비교는 계산 카드로 보여줄 수 있습니다. 하나의 단순 경로로 표현할 수 없는 집계·복합 조건을 가짜 경로로 포장하지 마세요.

절대 금지 사항:
- 답변을 만든 뒤 LLM에게 그럴듯한 탐색 과정을 작성하게 하는 것
- 조회하지 않은 노드·간선을 방문한 것처럼 표시하는 것
- 실제로 기록되지 않은 노드 방문 순서나 탐색 알고리즘을 꾸미는 것
- 실패한 조회·검증을 성공한 것처럼 표시하는 것
- LLM의 비공개 내부 사고 과정을 시스템의 검증 로그인 것처럼 제시하는 것

데이터베이스의 내부 노드 방문 순서를 알 수 없다면 이를 복원한 척하지 마세요. 실제 애플리케이션 조회 단계, 반환된 관계, 사용된 규칙의 순서까지만 표시합니다. 노드·간선 색상 변화나 순서 표시는 실제 실행 이벤트가 있는 범위에서만 사용하세요.

답변·그래프·규칙 결과·원문 근거는 동일한 실행 기록과 데이터 버전을 참조해야 합니다.


9. 프론트엔드와 자료 업로드 요구사항

프론트는 질문과 답변이 이어지는 하나의 채팅방 세션을 중심으로 구현합니다. 별도의 복잡한 설정 화면을 먼저 거치지 않아도 질문을 시작할 수 있어야 합니다.

입력 지원:
- 한국어 자연어 질문
- 이미지 업로드: 성적표, 교과 이수 현황 등
- PDF, HWP, DOCX 업로드
- 기존 대화와 업로드 자료를 참고한 후속 질문

출력 지원:
- 질문에 대한 직접적인 한국어 답변
- 펼쳐보기를 통한 실제 판단 과정, 관계 그래프, 규칙 검증, 원문 근거
- 필요한 경우 적용 조건, 인정 학점, 부족 조건을 보여주는 요약

기본 채팅 화면에는 결론과 핵심 정보만 보여주고, 사용자가 펼치면 “아, 내 이수 내역이 이 조건에 연결되어 이런 결과가 나왔구나”를 이해할 수 있게 구성하세요.

화면에 표시되는 노드·관계·단계 이름은 한국어 중심으로 표현합니다. 개발용 식별자는 내부적으로 유지하되 기본 화면의 이해를 방해하지 않도록 하세요. 그래프는 실제 답변에 사용된 부분을 중심으로 보여주고, 추가 탐색으로 조회한 관계는 원래 판정에 사용된 관계와 구분하세요.

업로드는 확장자만 허용하는 것으로 완료했다고 하지 마세요. 파일 내용을 추출하고 학생 정보로 정규화하여 질의에 활용하는 전체 경로가 작동해야 합니다.
- 텍스트 문서는 가능한 한 문서 파서를 우선 사용합니다.
- 성적표 이미지·스캔 문서는 필요할 때 문자 인식 또는 적절한 문서 인식 경로를 사용합니다.
- 과목명, 과목 코드, 학점, 이수 상태 등 판정에 영향을 주는 값의 추출 품질을 검증합니다.
- 불확실한 값이나 누락된 페이지·학기는 사용자에게 확인할 수 있게 합니다.
- 인식 실패나 일부 추출 성공을 전체 이수 내역 확인 완료로 취급하지 않습니다.
- HWP 등 형식별 실제 지원 범위와 파싱 실패 처리를 검증하고, 미지원 상태를 정상 지원처럼 표시하지 않습니다.

추가 업로드, 사용자 정정, 가정 시뮬레이션을 구분하고 대화 상태에 반영하세요. 다른 학생이나 다른 세션의 개인 데이터가 섞이면 안 됩니다. 업로드 문서 안의 지시문이 시스템 규칙을 변경하지 못하도록 하세요. 학생 자료를 외부 서비스로 임의 전송하지 마세요.


10. 평가 자료 사용 제한과 편향 방지

「교육과정 규칙 검증 승인 요청서.pdf」는 평가용 정답 자료입니다. 다음 용도로 사용하면 안 됩니다.
- 모델 학습, 파인튜닝, 정답 암기
- 런타임 시스템 프롬프트나 few-shot 예시에 문항·정답 삽입
- RAG 검색 문서, 임베딩 인덱스, 지식그래프의 사실·규칙 원천으로 적재
- 질문 문구별 하드코딩, 정답 캐시, 문항 전용 분기
- 승인 요청서의 정답을 교육과정 PDF에 없는 규칙으로 반영

평가 실행 시 질문은 일반 사용자 질문과 동일한 처리 경로로 입력하세요. 정답은 평가 도구에서만 비교하고, 답변 생성 경로에는 전달하지 마세요. 평가 자료를 앱의 런타임 검색 대상에서 분리하세요.

평가 결과는 다음 방식으로 개선에 활용합니다.
1) 실패를 질문 해석, 문서 추출, 개체 연결, 관계 누락, 적용 범위, 규칙 계산, 답변 표현, 근거 표시 등의 일반적인 유형으로 분류합니다.
2) 수정할 사실과 규칙의 근거를 교육과정 PDF에서 다시 확인합니다.
3) 특정 문항이 아니라 해당 오류 유형을 해결하도록 구조와 로직을 수정합니다.
4) 원문에 근거한 별도의 변형·경계·복합 질문과 단위 테스트로 일반화 여부를 확인합니다.

수정 방향을 정하는 데 반복적으로 사용한 평가 자료를 전혀 보지 않은 독립 최종 평가처럼 보고하지 마세요. 개발에 사용한 평가 결과와, 수정 과정에서 노출되지 않은 별도 평가 결과를 구분하세요. 문구만 바꾼 동일 문항을 독립적인 일반화 검증이라고 과장하지 마세요.

승인 요청서의 답변과 PDF가 충돌하거나 PDF에 없는 정보가 정답에 포함되어 있다면, 이를 별도로 보고하세요. 평가 점수를 맞추기 위해 규칙을 왜곡하지 마세요.


11. 현재 답변이 잘 안 되는 원인의 진단

현재 시스템을 실제로 확인한 뒤, 실패 사례별로 입력부터 화면까지 추적하세요. 아래 항목은 점검 대상이지 이미 확인된 원인이 아닙니다.

- PDF 표·각주·예외·적용 대상이 누락되거나 잘못 추출되었는가?
- 그래프가 문단 검색용으로만 구성되어 실제 의미 관계와 규칙이 부족한가?
- 과목, 이수 구분, 적용 교육과정, 학생 이수 정보가 올바르게 연결되어 있는가?
- 약칭·오타·대화 맥락을 처리하지 못해 다른 과목이나 조건으로 연결되는가?
- 복합 질문을 단순 키워드 검색으로 처리하고 있는가?
- 학점 계산, 대체 인정, 중복 제한, 예외 적용을 LLM이 추측하고 있는가?
- 적용 조건 선택이나 학생 정보의 완전성 판단에 문제가 있는가?
- 답변에 필요한 정보가 있는데도 과도하게 답변을 거부하는가?
- 조회·판정 결과는 맞는데 자연어 답변에서 수치나 결론이 달라지는가?
- 프론트의 그래프·과정 표시가 실제 실행 기록과 다른가?
- 평가 자료 유출이나 문항별 예외 처리로 성능이 과장되어 있는가?

각 문제는 “증상 → 실제 코드·데이터·로그 근거 → 원인 → 수정 방향 → 영향을 받는 질문 유형 → 검증 방법”으로 정리하세요. 프롬프트 조정으로 해결할 문제와 온톨로지·데이터·조회·검증 로직을 고쳐야 하는 문제를 분리하세요.

기존 구현에 재사용 가능한 구조가 있으면 보존하고, 정확성에 직접 영향을 주는 문제부터 우선순위를 정하세요.


12. 로컬 실행과 모델 선택

RTX 4070 Ti가 장착된 실제 PC의 VRAM, RAM, 운영체제, 기존 실행 환경을 확인하고 로컬 LLM 구성과 실행 방법을 결정하세요. 그래픽카드 이름만으로 가용 메모리나 성능을 단정하지 마세요.

한국어 질문 해석과 답변 표현에 적합한 모델·방법을 검토할 수 있습니다. 모델 선택은 실제 환경에서 구조화 출력 정확도, 약칭·맥락 해석, 응답 지연, 메모리 사용량을 비교하여 결정하세요. 확인하지 않은 벤치마크나 속도를 제시하지 마세요.

일반적인 질문 처리와 답변 생성에 외부 LLM API가 필수인 구성은 목표에 맞지 않습니다. 로컬 실행 여부와 외부 의존성을 구분하여 보고하세요.

모델 교체 전후에는 질문 해석 정확도와 검증 엔진 정확도를 별도로 측정하세요. 동일한 구조화 입력에 대한 판정 결과가 모델 교체 때문에 달라지면 역할 분리 실패로 취급하세요.


13. 검증 기준과 완료 조건

평가를 전체 정답률 하나로만 끝내지 마세요. 실제 수행한 범위에서 다음을 분리하여 검증하세요.
- 원문 사실·규칙의 추출 정확도와 구조화 범위
- 질문 의도 및 개체 연결 정확도
- 직접 사실 질문, 복합 관계 질문, 졸업 판정의 정확도
- 학점 합산·중복·대체·예외·경계값 처리의 정확도
- 정보 부족 시 과잉 판정과 불필요한 답변 거부의 발생
- 구조화된 결과와 최종 한국어 답변의 일치 여부
- 표시된 노드·간선·규칙·원문 근거와 실제 실행 기록의 일치 여부
- 이미지·PDF·HWP·DOCX의 실제 추출 및 질의 활용 여부
- 대화 상태 유지, 사용자 정정 반영, 세션 분리
- 로컬 실행, 메모리 사용량, 단계별 응답 지연

필수 테스트에는 다음을 포함하세요.
- 같은 의미의 정상 표현·약칭·오타·구어체 질문에서 판정 일관성
- 동일한 구조화 입력에 대한 반복 실행 및 모델 교체 시 판정 일관성
- 기준값 바로 아래·정확히 기준값·기준값 위의 경계 테스트
- 중복 이수, 대체 인정, 예외 적용, 정보 누락, 상충 입력
- 여러 관계와 조건을 동시에 사용하는 복합 질문
- 실제 이수 내역과 가정 시뮬레이션의 분리
- 원문에 없는 질문에 대해 없는 사실을 만들지 않는지 확인
- 최종 답변의 핵심 결론이 실행 기록과 원문까지 추적되는지 확인

최소 완료 기준:
1) PDF에서 직접 확인 가능한 주요 사실 질문이 정상 작동합니다.
2) 여러 관계와 규칙을 연결해야 하는 질문이 결정적 조회·검증으로 해결됩니다.
3) 모든 적용 조건이 확인·충족되면 “해당 PDF 기준 졸업 가능”이라고 판정합니다.
4) 미충족과 정보 부족을 혼동하지 않으며, 구어체·암시적 표현만을 이유로 답변을 거부하지 않습니다.
5) 관계 그래프와 판단 과정은 실제 실행 기록에서 생성됩니다.
6) 평가 정답이 런타임 지식·프롬프트·학습 데이터로 유입되지 않습니다.
7) 로컬 LLM이 정해진 역할로 실제 동작하고, 지원한다고 표시한 파일 형식은 전체 처리 경로가 검증됩니다.

수치 목표는 기존 평가 결과와 실제 측정 기준을 확인하여 명시하세요. 실행하지 않은 테스트, 측정하지 않은 성능, 확인하지 않은 지원 상태를 통과했다고 보고하지 마세요.


14. 작업 순서와 요구 산출물

자료와 저장소가 제공되어 있다면 다음 순서로 진행하세요. 계획만 나열하고 끝내지 말고, 접근 권한과 실행 환경이 허용하는 범위에서 구현과 검증까지 수행하세요.

1단계: 현재 상태 확인
- 입력 자료와 사용 경계를 정리합니다.
- 현재 온톨로지·그래프 스키마·적재 데이터·질문 처리 흐름·프론트 근거 표시·평가 경로를 확인합니다.
- PDF 규칙이 실제 데이터와 코드로 어떻게 연결되어 있는지 확인합니다.

2단계: 실패 원인 진단
- 평가 결과와 실제 실행 기록을 연결하여 원인을 분류합니다.
- 확인된 원인과 미확인 가설을 구분합니다.
- 정확성에 직접 영향을 주는 항목부터 개선 우선순위를 정합니다.

3단계: 목표 구조와 계약 설계
- 필요한 개체·관계·규칙·적용 범위·출처 구조를 정의합니다.
- 질문 해석 결과, 조회 입력, 판정 결과, 실행 기록, 프론트 표시 데이터의 계약을 정의합니다.
- 지식그래프와 결정적 검증 로직이 담당할 범위를 구체화합니다.

4단계: 구현·개선
- 필요한 데이터·관계·규칙을 원문에 근거하여 수정합니다.
- 자연어 해석, 조회, 계산·판정, 답변 검증을 분리합니다.
- 실제 실행 기록을 연결한 한국어 채팅 UI와 업로드 처리를 구현합니다.
- 기존 데이터와 기능에 영향을 주는 변경은 마이그레이션·호환성·복구 방법을 설명합니다.

5단계: 평가·회귀 검증
- 승인 요청서와 기존 평가 자료를 평가 전용 경로에서 실행합니다.
- 별도의 일반화·경계·회귀 테스트를 실행합니다.
- 실패를 숨기지 말고 결과와 수정 전후 차이를 보고합니다.

최종 보고에는 다음 내용을 포함하세요.
A. 현재 시스템 구조와 실제로 확인된 문제
B. 원인별 수정 방향 및 우선순위
C. 개선된 온톨로지·지식그래프·규칙 검증 구조
D. 대표 질문 유형별 기대 답변과 필요한 관계·검증 흐름
E. 실제 실행 기록에 연결된 한국어 UI 구성과 구현 내용
F. 변경한 파일·데이터·규칙, 로컬 실행 방법
G. 실제 테스트 결과, 평가 데이터 분리 여부, 남은 문제

D의 기대 답변은 교육과정 원문에서 독립적으로 도출하세요. 평가 정답을 재사용 가능한 런타임 예시집이나 정답 사전으로 만들지 마세요. 실제 자료가 없어 구체적인 답변을 확정할 수 없다면 변수형 답변 구조로 제시하고, 어떤 정보가 필요한지 명시하세요.


15. 가장 중요한 최종 원칙

이 프로젝트는 “LLM이 교육과정 PDF를 읽고 그럴듯하게 답하는 챗봇”이 아닙니다.

“교육과정의 사실·관계·규칙과 학생의 상황을 구조화한 시스템이 조회·계산·판정을 수행하고, 로컬 LLM은 질문을 해석하고 검증된 결과를 설명하며, 학생은 실제 관계와 규칙 적용 과정을 확인할 수 있는 조교형 소프트웨어”입니다.

모든 설계와 수정에서 다음을 지키세요.
- 정답의 근거는 기준 PDF와 확인된 학생 정보입니다.
- 판단의 중심은 지식그래프와 결정적 검증 로직입니다.
- LLM의 역할은 자연어 해석과 검증된 결과의 표현입니다.
- 평가 자료는 평가와 일반화 가능한 수정 방향 수립에만 사용합니다.
- 화면의 설명은 실제 실행한 과정만 보여줍니다.
- 성능 개선은 평가 문항 암기나 가짜 설명이 아니라 구조·데이터·로직의 개선으로 증명합니다.
